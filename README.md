# MCDiag Agent

Лёгкий плагин-агент телеметрии для серверов **Paper, Purpur, Leaf и других форков Paper 1.19.4+** (Java 17+). Собирает входы, выходы, смерти, SEVERE-ошибки, метрики (TPS, MSPT, online, entities) и **нагрузку от каждого плагина** и раз в 10 секунд асинхронно отправляет их батчем в MCDiag (`POST /api/v1/ingest`).

- Jar ≈ 90 KB, без зависимостей: только публичный Paper API, JSON собирается вручную.
- Память: буфер ограничен (по умолчанию 500 событий + 60 точек метрик + 10 минутных срезов профилировщика), в обычной работе меньше 150 KB.
- Влияние на TPS: в основном потоке выполняются только обработчики join/quit/death (хеш и одна строка), отметки начала и конца тика и подсчёт сущностей раз в 5 с. Сеть, метрики и профилировщик работают в других потоках.

## Установка

1. Скопируйте `MCDiag-Agent.jar` в `plugins/` и запустите сервер (или перезапустите, если он уже работал). Будет создан `plugins/MCDiag/config.yml`, при первом запуске в нём генерируется `uuid_salt`.
2. `backend_url` по умолчанию указывает на `https://mcdiag.rimworlda.ru/api/v1/ingest`. Меняйте его, только если панель работает на другом адресе (только `https://`).
3. Задайте токен **из консоли сервера**:
   ```
   diag token mcd_<serverId>_<uuid>
   ```
   Из чата команда запрещена: команды игроков пишутся в лог, и токен попал бы туда.

## Что собирается

| Событие | Поля |
|---|---|
| `join` | `ts`, `playerHash`, `nick` (0.7.0+), `firstJoin`, `world`, `ip` и `host` (0.7.0+, адрес входа из `Player#getVirtualHost`) |
| `quit` | `ts`, `playerHash`, `nick` (0.7.0+), `sessionSec` (из `Player#getLastLogin`) |
| `death` | `ts`, `playerHash`, `nick` (0.7.0+), `cause` (DamageCause), `killerType` (`PLAYER` / тип моба / `NONE`), `world` |
| `error` | `ts`, `logger`, `message` (≤ 512), `trace` (≤ 36 строк / 6000 символов) |
| метрика | `ts` (кратно 5 с), `tps`, `mspt`, `online`, `entities` |
| срез профилировщика (раз в минуту) | время главного потока по плагинам и частям ядра, CPU асинхронных потоков плагинов, средний и максимальный тик, лаг-спайки, процессор / heap / GC JVM |
| список плагинов (при старте и изменениях) | имя, версия, включён ли |
| системный срез (раз в минуту) | CPU процесса и машины, память JVM и машины, время GC, потоки, занятость диска, аптайм |
| метрика (0.3.0+) | плюс загруженные чанки и блоки-сущности |
| лаг-спайк (0.4.0+) | время, длительность, кто занимал тик, горячие методы; у первых трёх спайков минуты — до 20 строк лога плагинов |
| журнал команд (0.4.0+, только если включён в панели) | время, ник, команда после маскировки, плагин-владелец команды, мир |
| журнал чата (0.7.0+, только если включён в панели) | время, ник, текст после маскировки, мир, пометка `x`, если сообщение отменил другой плагин (мут, фильтр) |
| генерация мира (0.7.0+, раз в минуту) | сколько чанков сгенерировано впервые, по мирам; минуты без генерации не отправляются |
| экономика (0.7.0+, раз в 5 минут) | валюта (`vault` / `playerpoints`), имя плагина, название валюты, балансы игроков онлайн: хеш, ник, сумма |
| разбор спайка (0.5.0+) | путь вызова главного потока, чего он ждал, паузы GC, остановки JVM, долгий ввод-вывод (только имя файла или порт), выделено памяти за тик |
| карта памяти (0.5.0+, раз в минуту) | память процесса, куча, куча после GC, классы, код, буферы, потоки (в том числе по плагинам), кто выделяет память |

**Приватность.** UUID игрока превращается в `SHA-256(uuid_salt + uuid)`, а бэкенд дополнительно прогоняет этот хеш через HMAC со своим секретом. С 0.7.0 в событиях есть ник, а во входе — IP и адрес подключения: в панели их видят владелец и администраторы сервера, аналитик получает теги и замаскированные IP. Отключается ключами `collect.join_source` и `economy.enabled`. Чат и команды собираются только в журнале, который владелец включает в панели (см. «Журнал чата и команд»). Инвентарь не собирается. Объекты `Player`, `Entity`, `Location` и `Throwable` не хранятся: в буфер сразу попадает готовая строка.

Пример батча:

```json
{"batchId":"5b0e8c1a-3f2d-4a7b-9c11-2e4f6a8b9d00","sentAt":1793635210000,
 "plugin":{"version":"0.7.0","core":"leaf","mcVersion":"1.21.4"},
 "events":[
  {"type":"join","ts":1793635201234,"playerHash":"9f86d0…0a08","firstJoin":false,"world":"world"},
  {"type":"death","ts":1793635203456,"playerHash":"9f86d0…0a08","cause":"ENTITY_ATTACK","killerType":"ZOMBIE","world":"world"},
  {"type":"quit","ts":1793635207890,"playerHash":"9f86d0…0a08","sessionSec":6},
  {"type":"error","ts":1793635208000,"logger":"Minecraft","message":"Could not pass event PlayerJoinEvent to SomePlugin",
   "trace":"java.lang.NullPointerException: …\n\tat a.b.C.d(C.java:42)\n\t... 57 lines omitted ...\n\tat java.lang.Thread.run(Thread.java:833)"}
 ],
 "metrics":[{"ts":1793635205000,"tps":20.0,"mspt":11.9,"online":37,"entities":2850}]}
```

Всё, что не ASCII, экранируется как `\uXXXX`, поэтому длина тела в символах совпадает с длиной в байтах. Батч ограничен 60 KB при лимите бэкенда 64 KB.

## Журнал чата и команд

Чат и команды включаются в панели по отдельности, по умолчанию оба выключены. Команды нужны, чтобы видеть, кто и что выполнил перед лаг-спайком; чат — для модерации и чтобы знать своё сообщество.

- **Что пишется:** команды игроков и (0.7.0+) сообщения чата из `AsyncChatEvent`. Сообщения, отменённые мутом или фильтром, тоже пишутся с пометкой — так видно и то, что отсекли. Консоль, RCON и командные блоки не пишутся.
- **Что скрывается до отправки:**
  - команды со входом и паролями, например `/login`, `/register`, `/changepassword`, `/2fa`;
  - личные сообщения, например `/msg`, `/tell`, `/r`, `/mail`: остаётся только имя команды;
  - значение в `diag token`, токены и IPv4-адреса в любом тексте.
- **Как запретить на сервере:** `chat_log.allowed: false`. Панель тогда не сможет включить запись. Свои команды можно добавить в `chat_log.hidden_commands`.
- **Сколько хранится:** срок задаётся в панели, от 1 до 30 дней, по умолчанию 3. Журнал видят владелец и администраторы сервера.

Сообщите игрокам, что чат и команды записываются, например в правилах сервера.

## Генерация мира, экономика и заходы (0.7.0+)

- **Генерация мира.** `ChunkLoadEvent#isNewChunk` — одна проверка и одно сложение на загруженный чанк, счётчики потокобезопасны (Folia). Панель сравнивает MSPT в минуты с генерацией и без неё и советует предварительную генерацию (например, Chunky), если её нет.
- **Экономика.** Плагины валют находятся через reflection, без зависимостей в jar: Vault Economy (EssentialsX, CMI и другие) и PlayerPoints. Раз в 5 минут модуль читает балансы игроков онлайн в главном потоке, по 50 игроков за тик, и отправляет порциями до 100 игроков. Модуль запускается, только если панель объявила `economy`. Что найдено, показывает строка `Economy` в `/diag status`.
- **Заходы.** IP игрока и адрес из `Player#getVirtualHost` (домен или IP, к которому он подключился). Служебные части Forge и TCPShield отрезаются. За Velocity или BungeeCord домен входа знает только прокси.

## Модули журнала, сети и прав (0.8.0+)

Каждый модуль включается, только если панель объявила его раздел (`logs`, `net`, `audit`) и сервер на полном тарифе. Старая панель получает прежний формат.

- **Журнал логов (`logs`).** Appender на корневом логгере Log4j ядра видит всё: JUL-логгеры плагинов (ядро пересылает их в Log4j), SLF4J и ComponentLogger, `System.err` (`printStackTrace` склеивается обратно в одну запись) и сообщения самого сервера (`Can't keep up!`, watchdog, предупреждения ядра). Уровень WARN и выше. Одинаковые проблемы группируются по отпечатку (уровень, логгер, текст без чисел, UUID и IP, класс исключения, 3 верхних кадра): одна запись со счётчиком раз в 15 секунд, текст и трейс — только при первом появлении за час. Плагин определяется по логгеру, тексту («Could not pass event … to X») или первому кадру трейса из его jar. Серьёзность и влияние определяет панель по своим правилам. Перехват ставится в `onLoad` агента, поэтому видны и ошибки запуска других плагинов. Если log4j-core недоступен, остаётся корневой JUL Logger.
- **Сеть (`net`, `netreq`).** Обёртка над `ProxySelector` (ставится в `onLoad`): к нему обращаются HttpURLConnection, OkHttp, `java.net.http.HttpClient` и обычные `Socket` перед соединением. Ответ не меняется. Раз в минуту уходит сводка по хостам (`net`) и, с панелью 0.9.0+, подробности (`netreq`):
  - путь и параметры: запросы группируются по шаблону пути (числа, UUID, hex → `{id}`), у группы — последний пример целиком;
  - **секреты скрываются на сервере:** значения параметров `token`, `key`, `secret`, `password`, `auth`, `sig`, `session` и `modules.network.mask_params`, токены вебхуков Discord и ботов Telegram, длинные «случайные» сегменты пути — как `***(длина)`; длинные значения обрезаются до 200 символов;
  - плагин: по загрузчику класса (`JavaPlugin#getProvidingPlugin` — видны и затенённые библиотеки), затем по индексу jar-ов, затем по имени потока;
  - место вызова `класс.метод(Файл.java:строка)` и файл, из которого загружен класс (`plugins/Foo.jar`, `libraries/…`, путь вне папки сервера) — по ним можно найти источник, даже если плагин не определён;
  - частота, запросы из главного потока, поток, первый и последний запрос.
  В панели раздел «Безопасность» видят только владелец и администраторы.
- **Права (`privileges`).** Список OP сверяется раз в 10 секунд и сопоставляется с командами `/op` и `/deop` от игрока, консоли, RCON или командного блока: OP без команды — критичное событие (типичный бэкдор «слитых» плагинов). Права игроков онлайн проверяются по одному игроку раз в 2 секунды: опасное право (`*`, `luckperms.*`, `плагин.*`, админ-группы), выданное плагином через `PermissionAttachment`, записывается вместе с именем плагина. С LuckPerms агент читает его журнал действий и замечает опасные права, выданные без записи в журнале (через API). Команды управления правами (`/lp`, `/op`, `/pex` …) пишутся с маскировкой.

## Публичный API для плагинов

Агент регистрирует `net.mcdiag.api.McDiagApi` в `ServicesManager`. Подключите `mcdiag-api.jar` (собирается как `api/build/libs/mcdiag-api.jar`) как `compileOnly` и добавьте `softdepend: [MCDiag]`.

```java
McDiagApi api = McDiagApi.get();
if (api != null) {
    // Проблема появится в журнале ошибок панели со своей серьёзностью; повторы схлопываются в счётчик.
    api.report(this, Severity.HIGH, "payments.gateway", "Платёжный шлюз не отвечает 30 секунд");

    // Свой модуль: включается и выключается агентом, виден в /diag modules, задачи отменяются сами.
    api.registerModule(this, new AgentModule() {
        public String id() { return "shop-health"; }
        public void enable(ModuleContext ctx) {
            ctx.repeat(() -> { if (!gatewayOk()) ctx.report(Severity.HIGH, "payments.gateway", "Шлюз недоступен"); },
                    200, 1200, true);
        }
        public void disable() { }
    });
}
```

`ModuleContext` даёт модулю раздел `modules.<id>` из config.yml агента, логгер, возможности панели, определение плагина по классу и по стеку вызова и повторяющиеся задачи. Модуль, упавший при запуске, выключается без вреда для агента. Модули снимаются при выключении плагина-владельца.

## Разбор лаг-спайков и память

Появилось в 0.5.0.

- **Частые сэмплы при спайке.** Поток профилировщика следит за длительностью тика. Как только тик затягивается (примерно с 15 мс на здоровом сервере, но не позже половины `spike_threshold_ms`), снимки идут каждые `spike_interval_ms`.
- **Что делал поток.** Для каждого спайка агент находит вход (задача планировщика, событие, команда, пакет), путь вызова и то, чего ждал поток: диск, сеть, база данных, блокировка, загрузка классов, другой поток.
- **Что мешало извне.** JVM сама сообщает о паузах сборщика мусора. JFR сообщает об остановках JVM и долгом вводе-выводе. События приходят с задержкой, поэтому спайк уходит в панель примерно на 2,5 секунды позже.
- **Карта памяти.** Раз в минуту из MXBean и `/proc`. Если сервер запущен с `-XX:NativeMemoryTracking=summary`, раз в 5 минут добавляется разбор нативной памяти.
- **Поиск утечки.** Запускается владельцем в панели на 5–60 минут. JFR следит за выборкой объектов и показывает, какой код их создал. Снимков кучи агент не делает: они останавливают сервер.

**Защита сервера.** Снимки стека ограничены бюджетом (0,5% времени, в долгом тике 2%). Если JFR нет в сборке Java, он не запускается; если он тратит больше 3% ядра, агент выключает его сам. Ошибка внутри агента не попадает в консоль сервера как чужая проблема. Подробный разбор ограничен: 10 спайков в минуту и 120 в час, остальные идут кратко. JFR занимает примерно 10–20 МБ нативной памяти и до 16 МБ временных файлов.

**Совместимость.** Агент отправляет новые поля, только когда панель объявила их поддержку в ответе (`caps`). Со старой панелью он работает в прежнем формате: журнал и подробности спайков выключены, остальные данные приходят как раньше. Если панель отклонила батч с новыми полями, агент возвращается к прежнему формату.

## Тепловая карта и конверсия спавна

Показывает, какая доля игроков уходит со спавна в игру, какая выходит с сервера и что на это влияет. Пока модуль выключен или зона не задана, у него нет ни слушателей, ни задач. На старой панели, которая не объявила `heatmap`, и в бесплатном режиме он тоже не работает.

| Что считается | Как |
|---|---|
| Плотность | Позиции игроков в зоне раз в 5 секунд, клетка 2×2 блока, сводка раз в 5 минут. `PlayerMoveEvent` не используется |
| Визиты | Вход в зону, дошёл ли игрок до POI, чем закончил: ушёл пешком, телепортом, через портал, вышел с сервера или умер. Игрок передаётся хешем |
| Клики | Правый клик по блокам, контейнерам и NPC в зоне. Левые клики не считаются |
| Смерти | По всему серверу: ник, кто или что убило, чем, причина, координаты. Ники видит только владелец, срок хранения как у журнала команд |
| Рельеф | Верхний блок для каждой пары X/Z внутри зоны. Один чанк за 2 тика асинхронной загрузкой, новые чанки не генерируются, при MSPT выше 40 съёмка ждёт |

## Бесплатный режим

Панель сообщает режим в ответе на батч. В бесплатном режиме агент раз в 5 минут отправляет одну точку метрик и выключает профилировщик, JFR, буфер строк лога и тепловую карту. При продлении тарифа всё включается само, перезапуск не нужен.

## Диагностика по запросу поддержки

Если владелец сервера сам включит в обращении «Разрешить поддержке диагностику», поддержка MCDiag сможет попросить у агента:

| Команда | Что вернёт |
|---|---|
| `ping` | версия агента, аптайм, очередь и результат последней отправки |
| `status` | ядро, TPS 1/5/15, MSPT, онлайн, настройки агента — **без токена и соли** |
| `main_stack` | стек главного потока прямо сейчас (для зависаний) |
| `profile` | подробный профиль 10–120 с: сэмплы каждые 5 мс, доли плагинов и «горячие» методы |
| `plugins` | все плагины с версиями |
| `jvm` | версия Java, GC, аргументы запуска (значения `-D…` скрыты) |

Команды приходят в ответе панели на очередную отправку — входящих подключений к серверу нет. Все команды только читают: консольных команд, киков, перезапуска и изменения настроек среди них нет. Каждый запуск пишется в лог сервера: `Support diagnostics: <команда> done`. Набор команд зашит в агент, неизвестные игнорируются.

Если отправлять нечего, агент раз в 30 секунд шлёт пустой «пульс»: панель видит, что сервер на связи, а поддержка может передать команду.

## Профилировщик плагинов

Работает по тому же принципу, что Java-сэмплер [spark](https://spark.lucko.me/), но без интерфейса на сервере — графики, история и прогноз живут в панели MCDiag.

- **Главный поток.** Daemon-поток `MCDiag Profiler` в среднем раз в 50 мс смотрит на главный поток и записывает прошедшее время на плагин, чей код ближе всего к вершине стека. Если плагин вызвал API ядра, которое грузит чанк, время достаётся плагину, а не чанкам. Если плагина в стеке нет — части ядра: сущности, чанки, блоки, сеть, сохранение, прочее. Пока сервер ждёт следующего тика, стек не снимается вовсе. Интервал случайный: сэмплы с постоянным периодом 50 мс попадали бы в одну и ту же фазу тика.
- **Снимок стека.** На Java 19 и новее используется `Thread#getStackTrace`: приостанавливается только главный поток. На Java 17 единственный способ с ограничением глубины — `ThreadMXBean#getThreadInfo` (глубина 128), он останавливает всю JVM. Если снимки занимают больше 0,5% времени (внутри долгого тика 2%), агент сам снижает их частоту.
- **Чей класс.** Индекс пакетов строится по оглавлениям jar-файлов плагинов, классы не загружаются (поиск через загрузчик Bukkit писал бы в консоль «Loaded class … which is not a depend»). Пакет, который есть в нескольких jar, никому не приписывается — тогда сэмпл достаётся вызвавшему его плагину. Ответ для каждого класса кешируется.
- **Лаг-спайки.** События Paper `ServerTickStartEvent` / `ServerTickEndEvent` дают точную длительность тика. Как только тик затягивается, сэмплы снимаются каждые `spike_interval_ms` (по умолчанию 5 мс). Тики длиннее `spike_threshold_ms` сохраняются вместе с долями плагинов по сэмплам именно этого тика.
- **Асинхронная нагрузка.** Раз в 5 секунд читается CPU-время потоков планировщика Paper (`Craft Scheduler Thread - N - <плагин>`), `ForkJoinPool` и потоков с именем плагина. Обычно плагин виден по имени потока, и JVM не останавливается. Стеки безымянных потоков снимаются одним запросом, это одна остановка JVM на все такие потоки.
- **Логи к спайкам.** Хендлер только запоминает ссылку на строку, маскировка выполняется в потоке профилировщика и только для строк, которые прикладываются к спайку. При `spike_logs: false` и со старой панелью строки не запоминаются.
- **Счётчики мира.** Сущности, чанки и блоки-сущности считаются в главном потоке обходом, поэтому за один запуск (5 с) обходится один мир. Чанки и блоки-сущности обновляются в 6 раз реже. С несколькими мирами цифры обновляются реже, но новый мир учитывается сразу.
- **Стоимость.** Реальные цифры на вашем сервере показывает `/diag status`: снимков стека в секунду, их доля времени и собственный CPU профилировщика.
- **Точность.** Это оценка по сэмплам: код, который работает реже интервала, может не попасть в срез. На здоровом сервере за минуту набирается 200–300 снимков в тике, поэтому погрешность доли плагина за минуту составляет около 2–3% от занятого времени. За час она в 8 раз меньше.

### Отправка и повторы

- Пока предыдущий запрос не завершён, новый не создаётся.
- Неудачный батч (сетевая ошибка, 5xx, 429) хранится как готовая строка (≤ 60 KB) и повторяется **с тем же `batchId`**. Бэкенд отбрасывает дубли по `batchId`, поэтому таймаут после успешной записи не удвоит данные. Буфер в это время копит новые события в пределах своего лимита, лишнее вытесняется.
- Задержка между повторами растёт экспоненциально, до 5 минут. На 429 выдерживается `Retry-After`.
- 400 / 413: батч отбрасывается. 401 / 403 (токен недействителен или подписка неактивна): батч отбрасывается, пауза 60 с. В лог пишется только смена состояния, токен — никогда.

### Бюджет памяти

| Что | Обычно | Худший случай |
|---|---|---|
| Буфер событий (500) | ~75 KB | ~3,5 MB (500 ошибок по ~7 KB) |
| Буфер метрик (60) | ~5 KB | ~5 KB |
| Срезы профилировщика (10) | ~2–3 KB | ~40 KB |
| Кеш «класс → плагин» | ~200 KB | ~5 MB (50 000 классов, затем сброс) |
| Журнал логов (200 групп в окне, 400 в очереди) | ~20 KB | ~3 MB (группы с трейсами по ~7 KB) |
| Сеть (256 хостов + 256 групп запросов, по 512 в очереди) | ~10 KB | ~400 KB |
| Права (64 недавние команды, 500 записей в очереди) | ~2 KB | ~150 KB |
| Неотправленный батч | 0 | 60 KB |
| StringBuilder батча (переиспользуется) | 8–16 KB | 60 KB на время сборки |

## Ограничения

- Журнал логов использует log4j-core, который ядро несёт с собой (это не внутренние классы Paper или Leaf, а стандартная библиотека). Если конфигурацию Log4j перезагрузят, агент подключится заново в течение минуты.
- Без панели с разделом `logs` (старые версии) работает прежний сбор: только SEVERE с исключением через `java.util.logging`.
- Сетевой аудит не видит клиентов на NIO `SocketChannel` (Netty, Lettuce) и `HttpClient`, созданные до запуска агента. Метод (GET/POST) и тело запроса не видны: их нет в точке перехвата. У «голых» сокетов (`socket://`, базы данных) нет пути — видны хост, порт и место вызова.
- Кто именно выдал OP программно (`setOp`), узнать нельзя: у Bukkit нет такого события. Видно, что OP появился без команды.
- Под LuckPerms права, выданные через `PermissionAttachment`, видны как временные узлы (`lp_api`), без имени плагина.
- При выключении сервера неотправленный остаток (до одного интервала) теряется: в `onDisable` сетевые вызовы из основного потока запрещены.
- Folia не поддерживается.
- Строки лога у спайка берутся из того же перехвата Log4j; без него — из `java.util.logging`.
- Кисти WorldEdit работают без команды при каждом клике, поэтому в журнале и причинах спайка они не видны.
- Рельеф берёт верхний блок внутри зоны. Чтобы вместо крыши видеть то, что под ней, опустите верхнюю границу через `/diag pos1` или `/diag pos2` и снимите рельеф заново.
- Клики по NPC видны для Citizens, обычных торговцев и FancyNpcs. NPC других плагинов на пакетах могут быть не видны.
- Тепловая карта проверена тестами логики и демо-данными панели, а не под нагрузкой на живом сервере.
- Профилировщик видит код, загруженный из jar-файла плагина. Библиотеки, которые Paper скачивает по `libraries:` из plugin.yml, лежат отдельно — их время достаётся плагину, который их вызвал.

## Сборка

Нужен JDK 17+.

```bash
./gradlew build
```

Jar появится в `build/libs/MCDiag-Agent.jar`. Тесты (`./gradlew test`) проверяют экранирование JSON, обрезку стектрейса, буфер и лимиты батча, атрибуцию стеков, срезы профилировщика и стоимость сэмпла. Тест сборки батча пишет пример тела в `build/sample-batch.json`.
